### File: `app/web.py`
**Function/Class:** `create_app()` / Session Secret Handling  
**Severity:** 🔴 Critical  
**Category:** Reliability & Security  

**Problem:**  
When multiple Gunicorn workers start concurrently under Gunicorn (configured with `--workers 4`), they each execute `create_app()`. If the `.flask_secret` file does not exist yet, each worker process detects its absence, generates a unique secret key via `secrets.token_hex(32)`, and attempts to write it to the file. The last worker to write overwrites the file, resulting in a single key on disk. However, the other workers retain their own different in-memory keys. 

**Evidence:**  
```python
    secret_key = os.environ.get('FLASK_SECRET_KEY')
    if not secret_key:
        secret_file = Path(config.data_dir) / '.flask_secret'
        if secret_file.exists():
            with open(secret_file, 'r') as f:
                secret_key = f.read().strip()
        else:
            secret_key = secrets.token_hex(32)
            try:
                with open(secret_file, 'w') as f:
                    f.write(secret_key)
                os.chmod(secret_file, 0o600)
```

**Impact:**  
Users will experience random, sporadic logouts and session invalidation as their requests are routed to different Gunicorn worker processes using different Flask secret keys. 

**How To Reproduce:**  
1. Delete `.flask_secret` if it exists.
2. Start the Docker container with `docker compose up -d`.
3. Log in to the application.
4. Refresh the page repeatedly. Gunicorn will route requests round-robin to different workers, resulting in immediate unauthorized redirects or session failures.

**Recommended Fix:**  
Ensure Flask secret generation uses file-locking or is handled as part of an initialization script before the Gunicorn web server starts, or enforce that `FLASK_SECRET_KEY` must be set in the environment variables for production environments.

**Example Fix:**  
```python
# Before starting Gunicorn, run a script to initialize `.flask_secret` if missing.
# Alternatively, use file locking in python during web app initialization:
import fcntl

# ...
        else:
            try:
                # Open with lock to prevent race condition
                with open(secret_file, 'a+') as f:
                    fcntl.flock(f.fileno(), fcntl.LOCK_EX)
                    f.seek(0)
                    content = f.read().strip()
                    if content:
                        secret_key = content
                    else:
                        secret_key = secrets.token_hex(32)
                        f.write(secret_key)
                        os.chmod(secret_file, 0o600)
            except Exception:
                # Fallback to in-memory key
                secret_key = secrets.token_hex(32)
```

### File: `app/web.py`
**Function/Class:** `get_current_prices()` / Dashboard API Loading  
**Severity:** 🔴 Critical  
**Category:** Scalability & Backend Architecture  

**Problem:**  
The dashboard price loading endpoint fetches real-time data from the NSW/TAS Fuel Check API *synchronously* during the request lifecycle. Because this API call blocks the synchronous Flask worker threads, if the external Fuel Check API experiences latency, timeouts, or high response times, all Gunicorn worker threads will quickly become exhausted and block.

**Evidence:**  
```python
@app.route('/api/prices/current', methods=['GET'])
@login_required
def get_current_prices():
    """Get current fuel prices from the API."""
    cfg, ftr = refresh_config_and_fetcher()
    # ...
    data = ftr.fetch_station_price_data(stations_list)  # Synch wrapper running asyncio.run()
```

**Impact:**  
A single user opening or refreshing the dashboard causes a slow synchronous outbound network call. Under a modest load of 10 concurrent requests, the entire Gunicorn thread pool will be blocked, rendering the web interface unresponsive to all other users.

**Recommended Fix:**  
Decouple the Web UI from the external API completely. The Flask endpoint should only read station and price data from the local SQLite/InfluxDB databases where the background scheduler updates them.

**Example Fix:**  
```python
@app.route('/api/prices/current', methods=['GET'])
@login_required
def get_current_prices():
    # Read prices from InfluxDB or cache DB directly instead of calling NSW/TAS API live
    # Fetch from local DB is O(1) and extremely fast
    cfg, _ = refresh_config_and_fetcher()
    # ...
    # Query SQLite database or InfluxDB cache instead of fetcher.fetch_station_price_data()
```

### File: `app/web.py`
**Function/Class:** Flask Configuration & CSRF  
**Severity:** 🔴 Critical  
**Category:** Security  

**Problem:**  
The application uses Flask sessions for authentication but does not implement CSRF (Cross-Site Request Forgery) protection on standard form submissions (like login, setup) or any of the state-changing REST API endpoints (`/api/config`, `/api/stations`, etc.).

**Evidence:**  
No inclusion of Flask-WTF or custom CSRF tokens in templates or request verification routes.

**Impact:**  
An attacker can host a malicious webpage that executes background API calls to the user's local instance (e.g., modifying MQTT configuration, adding malicious station configurations, or disabling authentication).

**Attack Scenario:**  
An authenticated administrator visits an attacker-controlled site. The site contains a hidden form that POSTs to `http://localhost:5000/api/config` to change `auth_enabled` to `false` or update the MQTT password.

**Recommended Fix:**  
Install `Flask-WTF` and enable CSRF protection globally on the Flask application.

### File: `app/web.py`
**Function/Class:** Gunicorn In-Memory Configuration  
**Severity:** 🟠 Major  
**Category:** Backend Architecture  

**Problem:**  
When Gunicorn runs with multiple worker processes, modifications to the application configuration (such as adding a station, deleting a station, or updating credentials) only update the database and the in-memory config of the *particular* worker handling the request. The other Gunicorn workers keep their old in-memory configuration until a subset of routes refresh it, leading to inconsistent application states.

**Evidence:**  
```python
@app.route('/api/stations', methods=['POST'])
@login_required
def add_station():
    # ...
    # Add station to database
    if config.db and config.db.add_station(station_id, fuel_types, au_state, discount):
        # Update in-memory config
        new_station = { ... }
        config.stations.append(new_station)  # Modifies in-memory config ONLY in current worker
```

**Impact:**  
Users will see added stations disappear and reappear depending on which Gunicorn worker handles their requests.

**Recommended Fix:**  
Read configuration details directly from SQLite on every request or use a shared key-value store. Avoid modifying in-memory lists like `config.stations` inside worker lifecycles.

### File: `app/web.py`
**Function/Class:** `_check_rate_limit()`  
**Severity:** 🟠 Major  
**Category:** Security & Reliability  

**Problem:**  
The simple in-memory rate limiter uses a global Python dictionary `_login_attempts` that grows without bound as new IP addresses make requests. Furthermore, because it is in-memory, the rate limits are not shared across the 4 Gunicorn workers, and are wiped when workers restart.

**Evidence:**  
```python
_login_attempts: Dict[str, list[float]] = {}

def _check_rate_limit(key: str, max_attempts: int = 5, window_seconds: int = 60) -> bool:
    # ...
    attempts = _login_attempts.setdefault(key, [])
```

**Impact:**  
1. Distributed brute-force attacks are highly effective because the rate limiting is segmented across workers.
2. In-memory storage creates a memory leak over time under a high volume of unique IP requests.

**Recommended Fix:**  
Use a Redis backend for rate-limiting, or utilize SQLite database transactions to record and clear login attempts.

### File: `app/data.py`
**Function/Class:** `fetch_station_price_data()` / Timeouts  
**Severity:** 🟠 Major  
**Category:** QA & Reliability  

**Problem:**  
The aiohttp `ClientSession` is initialized without any network timeout settings.

**Evidence:**  
```python
async def _fetch():
    async with aiohttp.ClientSession() as session:
        client = NSWFuelApiClient( ... )
```

**Impact:**  
If the NSW/TAS Fuel API endpoint experiences socket hangs, the requests will remain open indefinitely (up to default TCP timeout limits), blocking resources.

**Recommended Fix:**  
Enforce strict timeouts (e.g., 10 seconds connect/read) on the `ClientSession`.

**Example Fix:**  
```python
timeout = aiohttp.ClientTimeout(total=10)
async with aiohttp.ClientSession(timeout=timeout) as session:
```

### File: `docker-compose.yml`
**Function/Class:** Service Definitions  
**Severity:** 🟠 Major  
**Category:** Infrastructure  

**Problem:**  
No resource constraints (CPU/Memory limits) are configured in `docker-compose.yml` for `influxdb`, `fuelapp`, or `grafana`.

**Impact:**  
A runaway query, database leak, or container failure could consume the entire host system's memory and CPU, crashing the machine.

**Recommended Fix:**  
Specify memory and CPU limits inside the service configurations.

**Example Fix:**  
```yaml
deploy:
  resources:
    limits:
      cpus: '0.50'
      memory: 512M
```

### File: `app/config.py`
**Function/Class:** `ConfigDatabase`  
**Severity:** 🟡 Minor  
**Category:** Database & Reliability  

**Problem:**  
SQLite database operations do not handle thread safety using a connection pool, and the connection is kept open indefinitely. While `check_same_thread=False` is set, SQLite is not fully thread-safe without strict serial write operations.

**Recommended Fix:**  
Utilize a scoped session pattern or database connection pooling (like SQLAlchemy) instead of maintaining a single global connection pointer.

## 4. EXECUTIVE SUMMARY

### Is this production ready?
**No.** The application is not production-ready and cannot safely serve paying customers.

### Biggest Business Risks:
1. **Denial of Service under Minimal Load**: Because the app fetches prices synchronously on page load, a few concurrent requests to the dashboard will exhaust all Gunicorn worker threads.
2. **Account Compromise & Session Issues**: Lack of CSRF protection exposes users to account-takeover style attacks. Additionally, session desynchronization will cause constant customer complaints about login issues.
3. **Missing Regression Protection**: With zero automated tests, any updates risk introducing severe bugs.
